# CreatorOps 迭代路线图

> **用途**：面向产品负责人/管理层的下一次迭代规划。回答三个问题：**先做什么、为什么是这个顺序、怎么算做成了**。
> **本文的立场**：路线图不是"想做什么"的清单，而是**在约束下排出的顺序**。本项目的最大约束不是功能缺口，而是**工程验证的缺口**——所以 P0 全是"让已有代码可被证明正确"，而不是加新功能。

---

## 1. 战略判断：未来 12 个月的三个基本盘

### 判断一：当前主要矛盾不是功能不足，而是"无法证明已建的能跑"

- 后端 88 源文件、前端 64 个 `.ts|.tsx`、18 张业务表、7 类 AI 任务、39 个权限点——**功能面已经相当完整**；
- 但单测/e2e/构建/迁移/容器化**从未在正常环境执行过**（`README.md` §10 自述），且已核实存在 3 处会让 CI 与部署直接失败的缺口；
- 结论：**可验证性本身就是产品特性**。一个"财务不能验证金额正确性"的结算系统，功能再多也不敢上线。

### 判断二：AI 的价值还没被"证明"，只被"记录"了

- 现状已具备：token/成本/耗时/降级原因/人工采纳率全部落库，有月度预算熔断；
- 缺失的是**AI 采纳 → 业务结果**的关联：采纳了 AI 脚本的内容，其完播率/转化/流水是否真的更好？不知道；
- 结论：AI 侧下一阶段的主题不是"加更多 AI 功能"，而是**从"AI 可用"走到"AI 的 ROI 可证明"**。

### 判断三：真实数据的依赖在外部，需要并行推进而非等到最后

- 平台采集是适配器骨架，真实接入需要**企业资质 + 逐平台联调**——这是长周期外部依赖；
- 结论：资质申请与平台联调必须**现在就并行启动**，不能排在最后，否则整个看板与结算的真实性会被卡住。

### 路线图三原则

| 原则 | 含义 | 反例（我们要避免的） |
| --- | --- | --- |
| **先可证，再新增** | 任何新功能之前，已有功能必须可被验证 | 在测试跑不起来的情况下继续加模块 |
| **先内控，再效率** | 资金与权限的加固优先于操作便利性优化 | 为了"少点两次"而放宽审批校验 |
| **先度量，再投入** | AI 与采集的投入规模由度量结果决定 | 因为"AI 是趋势"就继续加 AI 功能 |

## 2. 路线图总览

```
Phase 0  · 可上线（0–2 周）      「让已有代码可被证明正确」
          主题：验证 + 基础设施闭环
          出口标准：四道 CI 关卡全绿，空库能 migrate deploy

Phase 1  · 可运维（1–3 个月）    「让系统能被安全地规模化运行」
          主题：多实例安全 + 前端可测性 + 目录重构
          出口标准：双实例部署不出错、前端有真实测试

Phase 2  · 可证明价值（3–6 个月）「让 AI 的 ROI 从"记录"变成"可对比"」
          主题：AI 采纳 ↔ 业务效果关联 + 成本效率优化
          出口标准：能回答"哪类 AI 任务值得继续投入"

Phase 3  · 可规模化（6–12 个月）「数据量、多品牌、合规三线扩展」
          主题：搜索能力 / 多租户 / 密钥轮换 / 平台真实接入
          出口标准：数据量 10 倍后看板 P95 仍达标、支持多品牌隔离
```

## 3. Phase 0 · 可上线（0–2 周）

**主题**：验证与基础设施闭环。**本阶段不加任何新功能。**

### 3.1 交付项

| # | 交付项 | 具体动作 | 验收标准 | 负责角色 | 预估 |
| --- | --- | --- | --- | --- | --- |
| 0.1 | **跑通完整工具链** | `pnpm install → prisma generate → -r typecheck → test:cov → migrate+seed×2 → test:e2e → build` | 全部退出码 0；测试首次真实执行通过 | 后端 | 2–3 人日 |
| 0.2 | **补初始建表迁移**（阻断项 B-1） | 从现有 `schema.prisma` 生成初始迁移，与既有 2 个手写迁移对齐顺序 | 空库 `migrate deploy` 后 `\dt` 列出 18 张表 + `_prisma_migrations` | 后端 | 0.5 人日 |
| 0.3 | **补 api eslint 配置**（阻断项 B-2） | 补 `eslint` + `@typescript-eslint/*` 依赖 + `apps/api/.eslintrc.cjs`；顺手修 `package.json` 中 `verify`/`lint` 同行问题 | `pnpm -r lint` 退出码 0 | 后端 | 0.5 人日 |
| 0.4 | **补 `apps/api/Dockerfile`**（阻断项 B-3） | 多阶段构建（deps → build → runner），非 root 用户运行；或明确移除 compose 中的 api/web 服务 | `docker compose --profile full build` 成功 | SRE + 后端 | 1 人日 |
| 0.5 | **覆盖率阈值校准** | 现有阈值 `lines/functions/statements 60 / branches 55` 是设计值；按首次真实结果决定"补测试到阈值"还是"先按模块分级设阈值" | CI 覆盖率关卡稳定通过 | 后端 | 1–2 人日 |
| 0.6 | **前端最小测试集** | 补 3 类关键测试：① `PermissionGate` 权限门 ② 金额格式化（只格式化不运算）③ 401 并发去重刷新 | web 侧 vitest 有真实产出 | 前端 | 2 人日 |
| 0.7 | **验证文档同步更新** | 把 `README.md` §10「未能验证」清单逐项改为已验证结果；把 3 个阻断项的修复写入 `deployment.md` | 文档与事实一致，无"文档说有、实际没有"的文件引用 | 全员 | 0.5 人日 |

### 3.2 出口标准（Go/No-Go 判据）

- [ ] 四道 CI 关卡全绿（静态校验 / 单测+覆盖率 / 集成+e2e / 构建）
- [ ] 空库能 `prisma migrate deploy` 建出全表，`db:seed` 连跑两次结果幂等
- [ ] 3 个阻断项全部闭合并在评审记录中关闭
- [ ] `docs/` 中不再存在指向不存在文件的描述

### 3.3 本阶段明确不做

不加新功能、不重构页面、不动数据库结构（除补迁移）、不优化性能。**理由：在验证基础建立之前做任何改动，都无法判断是"改坏了"还是"本来就没跑通"。**

## 4. Phase 1 · 可运维（1–3 个月）

**主题**：让系统能被安全地规模化运行。

| # | 交付项 | 解决什么问题 | 验收标准 | 优先级 |
| --- | --- | --- | --- | --- |
| 1.1 | **定时任务选主** | 多实例部署时每个实例都会触发（重复日志 + 无谓 DB 压力） | 双实例并发跑月度结算：只出一次账、日志无重复 | P1 |
| 1.2 | **限流存储切 Redis** | 内存限流在多实例下阈值放大 N 倍，登录失败锁定可被绕过 | 双实例下连续错误密码在第 5 次被锁定 | P1 |
| 1.3 | **前端可测性重构** | 三个千行页面（1014/915/912 行）无法测试与复用 | ① 抽公共轮询 hook（消除重复 `refetchInterval`，切页停止轮询）② 单文件 < 600 行 | P1 |
| 1.4 | **数据范围与归属校验的全量审计** | 三级校验的第 3 级靠人工在 Service 调用，漏一处即越权 | 遍历所有按 ID 的入口，逐一确认有归属复核；补遗漏项 | P1 |
| 1.5 | **「AI 不得改写关键字段」变成代码保障** | 当前是规范约定（"没有这么做"），不是机制（"不允许这么做"） | 在 Service 层禁止 AI 输出直接进入 `Settlement`/`Contract`/`Creator.status` 写入路径 | P1 |
| 1.6 | **登录限流策略复核** | 密码尝试锁定若基于内存，安全性不足 | 与 1.2 合并验证 | P1 |
| 1.7 | **慢查询与索引治理** | 关键词搜索 `contains + insensitive` 走不了索引 | 万级数据下主要列表接口 P95 < 500ms | P2 |
| 1.8 | **移除无效依赖 / 顺手指纹清理** | `zustand` 全仓 0 处使用；Modal/Drawer 无 focus trap | 依赖树无未使用包；弹层键盘可达 | P2 |

**出口标准**：双实例部署下无重复出账、无限流绕过；前端有覆盖关键交互的测试；数据范围校验有全量核对记录。

## 5. Phase 2 · 可证明价值（3–6 个月）—— AI PM 的核心阶段

**主题**：把 AI 从"有记录"推进到"ROI 可对比"。

### 5.1 核心交付：AI 采纳 ↔ 业务效果关联

现在的 `/api/ai/usage` 能回答"花了多少 / 花在哪类任务 / 采纳率多少"，但回答不了**"采纳了 AI 建议的内容，效果真的更好吗"**。

| # | 交付项 | 具体设计 | 验收标准 |
| --- | --- | --- | --- |
| 2.1 | **效果关联数据层** | 将 `AiTask`（`humanFeedback=1` 采纳）与 `Content` 的效果指标（`completionRateBp`/`viewCount`/`conversions`/`revenueCents`）关联 | 可 SQL 直接查出"AI 生成脚本的内容 vs 人工脚本的内容"效果对比 |
| 2.2 | **归因口径定义（关键）** | 明确对照组：同一达人同时期、同垂类、同平台的内容；排除账号成长、投放、季节性干扰 | 口径写入 `docs/ai-guidelines.md`，评审通过 |
| 2.3 | **AI ROI 看板** | 展示：每类任务的 单位成本 / 采纳率 / 采纳后效果差 / 综合 ROI | 管理者可据此决定"哪类任务值得继续投入、哪类应下线" |
| 2.4 | **Prompt 版本 A/B 效果对比** | 现有 `rolloutPercent` 灰度 + 版本化已支持分流，补齐"版本 × 效果"的对比视图 | 能回答"v2 比 v1 效果更好吗" |
| 2.5 | **成本效率优化** | 按任务类型设不同预算上限；低价值任务（如日报）改用更便宜模型 | AI 单位成本下降且采纳率不降 |
| 2.6 | **AI 能力下线机制** | 明确"采纳率低于 X% 且 ROI 为负 → 下线"的规则与流程 | 至少完成 1 次"基于数据下线某能力"的决策 |

### 5.2 为什么这个阶段最有价值

> 现在的 AI 治理已经做到了"**可观测**"，但没做到"**可判断**"。区别是：可观测能回答"AI 花了多少钱"，可判断才能回答"这钱该不该花"。**这是 AI 功能从"试点"走向"长期存在"的唯一路径。**

### 5.3 出口标准

- 能用一张图回答"哪类 AI 任务值得继续投入"；
- 至少完成一次"基于数据砍掉或调整某个 AI 能力"的决策并留档；
- AI 单位成本（分/任务）有可对比的月度趋势。

## 6. Phase 3 · 可规模化（6–12 个月）

| # | 交付项 | 触发条件（不是"技术先进性"） | 验收标准 |
| --- | --- | --- | --- |
| 3.1 | **搜索能力升级** | 达人/内容数据量到十万级，关键词搜索 P95 超 1s | 引入 `pg_trgm` GIN 或独立搜索服务，P95 < 300ms |
| 3.2 | **候选下拉接口** | 筛选需输入 UUID，万级数据下无法拉全量拼下拉 | 按关键词返回候选列表的轻量接口，前端下拉免输 UUID |
| 3.3 | **白标多租户** | 出现第二家公司/品牌方需要数据隔离 | `Team` 之上加分租户维度，数据范围自动收敛，跨租户不可见 |
| 3.4 | **敏感字段密钥轮换** | 合规要求或密钥泄露应急演练 | 密文 `v1` 前缀的双读迁移落地，可无损轮换 KMS 数据密钥 |
| 3.5 | **平台真实数据接入** | **外部依赖：企业资质 + 逐平台联调**（须在 Phase 0 就启动申请） | 至少 1 个平台 `dataSource=API_OFFICIAL` 的真实数据进入看板与结算 |
| 3.6 | **账号级手动采集端点** | 运营需要按需刷新单个账号数据 | `POST /api/accounts/:id/sync` 上线，前端按钮不再提示"接口未开放" |
| 3.7 | **看板性能预聚合** | 内容表到千万级，看板聚合变慢 | 按天预聚合表 + Redis 缓存，接口契约不变 |
| 3.8 | **外部告警通道** | 需要企微/钉钉即时推送（现仅站内通知） | 接入 `ALERT_WEBHOOK_URL`，关键事件实时推送 |

### 3.x 刻意不做（并记录理由）

| 不做 | 理由 | 何时才该做 |
| --- | --- | --- |
| 微服务拆分 | 团队规模小，分布式事务与联调成本 > 收益 | 模块由不同团队独立发布且需独立扩缩容 |
| 消息队列中间件 | 当前唯一异步场景是定时与采集 | 需削峰（十万级批量导入）或事件驱动多消费者 |
| 接入真实支付通道 | 内部工具现状是"人工打款 + 凭证回填"，不应越界做资金通道 | 业务明确要求自动化付款且有支付合规能力 |
| ORM 二级缓存 | 缓存与库不一致是资金系统灾难来源 | 只读报表成瓶颈时用物化视图，而非二级缓存 |

| 类型检查错误数 | **未验证**（strict 已开） | 0 |

### 8.2 运行健康度（Phase 1 起跟踪）

| 指标 | 目标阈值 |
| --- | --- |
| 接口 P95 延迟 | < 1s（看板聚合 < 2s） |

| 指标 | 定义 | 为什么重要 |

### 8.4 AI 效能（Phase 2 的核心）

| 指标 | 现状 | 目标 |
| --- | --- | --- |
| 各任务类型采纳率 | **已可查**（`humanFeedback`） | 逐类设定基线，低于基线触发下线评审 |
| AI 月度成本 vs 预算 | **已可查**（`/api/ai/usage`） | 不超预算；单位成本逐月下降 |

| 输出结构失败率（`SCHEMA_MISMATCH`） | **已可查** | 逐月下降（反映 Prompt 质量） |

| **每类 AI 任务的 ROI** | **不可查（本阶段要补）** | 有正 ROI 的保留，负 ROI 的下线 |

## 9. 风险登记册（与路线图联动）

| 风险 | 概率 | 影响 | 应对 | 触发信号 |
| --- | --- | --- | --- | --- |
| 迁移不足导致生产无法建库 | 高 | 极高 | Phase 0 的 0.2 优先做 | `migrate deploy` 到空库失败 |
| 首次跑测试暴露大量真实缺陷 | 高 | 中高 | Phase 0 预留缓冲，不承诺并行新功能 | 单测/e2e 出现失败用例 |
| 平台资质与联调周期不可控 | 中 | 高 | **现在启动申请**；期间明确标注 `MOCK` 数据 | 资质审批延迟 |
| AI 效果关联被混淆因素干扰 | 高 | 中 | 先定义口径与对照组，用小样本预研 | 效果差异不显著或波动大 |
| 多实例部署后定时任务重复 | 中 | 中 | Phase 1 的 1.1；业务幂等已兜底不出错数据 | 双实例日志出现重复任务记录 |
| 千行页面重构引入回归 | 中 | 中 | 先补测试再重构，Phase 1 只抽 hook | 重构后无测试覆盖 |
| 密钥轮换未做导致泄露无法收敛 | 低 | 高 | Phase 3 的 3.4；当前 `v1` 前缀已预留 | 合规审计要求或密钥泄露事件 |

## 10. 一页交付摘要（给管理层的版本）

```
【战略判断】
  功能面已完整，主要矛盾是"无法证明已建的能跑"。
  因此近期资源优先级 = 验证与基础设施，而不是新功能。

【Phase 0 · 0–2 周】可上线
  跑通完整工具链 + 补 3 处基础设施缺口（初始迁移 / api lint / api Dockerfile）+ 前端最小测试集
  出口：四道 CI 关卡全绿，空库能 migrate deploy

【Phase 1 · 1–3 个月】可运维
  定时任务选主 + 限流切 Redis + AI 输出写入加固 + 前端可测性重构
  出口：双实例部署不出错、越权风险有全量核对记录

【Phase 2 · 3–6 个月】可证明价值（AI PM 核心阶段）
  AI 采纳 ↔ 内容效果关联 + ROI 看板 + Prompt A/B + 能力下线机制
  出口：能回答"哪类 AI 值得继续投入"，并完成一次基于数据的下线决策

【Phase 3 · 6–12 个月】可规模化
  搜索升级 + 多租户 + 密钥轮换 + 平台真实数据接入
  出口：数据量 10 倍后性能达标、支持多品牌隔离

【现在就要并行启动的一件事】
  平台数据采集的企业资质申请与逐平台联调（长周期外部依赖，不能排在最后）
```
