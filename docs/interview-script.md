# CreatorOps · 面试讲解稿

> **用途**：把 CreatorOps 讲给面试官/技术负责人听。
> **使用方式**：先读 §1 定基调，再按面试时长选 §2（项目介绍）的版本，最后用 §3 的口径回答追问。
> **一条纪律**：**不夸大验证状态**。本项目有明确的"未验证清单"（见 §4），主动说出来比被问出来强得多——面试官最想确认的恰恰是你是否清楚自己交付物的边界。

---

## 1. 先定基调：一句话价值主张

三句话版本（60 秒，用于自我介绍环节）：

> 我做的是一个**达人合作全流程管理系统**，业务是从"找达人 → 谈合同 → 做内容 → 看数据 → 算钱 → 打款"这条链路。
>
> 它的核心不是 CRUD，而是**把"钱算得准、权管得住、事追得到"这三件事做成了可被断言、可被穷举测试、可被复算复现的工程机制**——比如结算引擎是一个无 IO 的纯函数，每次计算后都会断言「平台费 + 公司分成 + 达人分成 === 总流水」，从数学上消除了"三笔加起来比总流水少一分"这个财务对账的经典问题。
>
> 另外 AI 在这个项目里不是功能装饰，而是**被当成有成本、会出错、必须被度量的外部依赖来治理**：每次调用都落库 token/成本/耗时/人工采纳率，有月度预算熔断、有降级可见、有输出结构强校验。

**为什么这样定基调**：面试官每天听"我做了个管理系统"，只有当你给出**一个别人抄不走的机制**时，对话才会从"你做了什么"升级到"你怎么想的"。

## 2. 分时长讲解脚本

### 2.1 90 秒版（电梯陈述）

```
【背景 15s】达人孵化与内容商业化业务，链路是：招募达人 → 签合同 → 生产内容 → 分发平台 → 按流水与品牌/达人分账。
            原来的痛点是达人信息散在 Excel/微信里，结算靠人用 Excel 手算，多级抽成加代扣税，尾差累积、口径不一，达人对账不信任。
【做了什么 30s】我做了一套系统把这条件链路收进来：统一达人库 + 合同内嵌分润规则 + 内容数据采集 + 结算引擎 + 审计。
            关键设计是——合同不是文档，而是结算引擎的参数源；内容是最小的结算归因单元；达人合作生命周期是状态机而不是自由字段。
【最硬的一点 30s】最难的是"钱算得准"。我把结算做成无 IO 的纯函数，金额全程用「分」的整数和基点整数算，绝不用浮点；
            并且公司分成不是独立相乘，而是用「净额减达人分成」反推，这样守恒恒等式天然成立。
            幂等做了三层：数据库唯一约束 + 明细幂等键 + 已审批跳过，所以定时任务可以放心重跑，绝不会重复出账。
【AI 15s】AI 侧我做了 7 类任务嵌在业务节点上（脚本生成、达人匹配、合规预检、结算异常解释等），
            全部有成本熔断、结构化校验、降级可见和采纳率统计——能回答"AI 花在哪、值不值"。
```

### 2.2 5 分钟版（技术深挖，按这个顺序讲）

**第 1 步：业务建模的三个洞察（60s）**

| 洞察 | 具体做法 | 解决什么 |
| --- | --- | --- |
| 合同 = 分润参数源 | `Contract` 直接存 `platformFeeBp / agencyShareBp / talentShareBp / taxWithholdBp / tieredShares`，结算读合同算钱 | "结算时才发现这份合同是 7:3 还是 6:4"的扯皮 |
| 内容 = 结算最小单元 | 一条内容只在一个账期结算一次（按发布月归因） | 跨月重复计算 |
| 生命周期 = 状态机 | 达人 8 态，非法流转返回 409 + `allowedNext` | "给已解约的达人排期""给线索出结算单" |

**第 2 步：资金正确性（120s）——这是全场重点**

讲四个层次，层层递进：

1. **存储层**：金额 `Decimal(18,2)`，绝不用 `Float/Double`；比率用基点整数（`7000` = 70%），避免 `0.7` 的浮点表示问题。
2. **计算层**：全部转「分」的整数运算。关键是**尾差处理**——平台费向下取整、达人分成向上取整、**公司分成用"净额减达人分成"反推**。这样 `平台费 + 公司 + 达人 === 总流水` 是恒等式，不是"应该相等"。
3. **断言层**：每次计算后都断言守恒，不守恒直接抛错——**这是代码缺陷而非业务问题，不能让它算出一个错数继续往下走**。
4. **幂等层**：`Settlement @@unique([creatorId, periodStart, periodEnd])` + `SettlementItem.idempotencyKey` 唯一 + 已审批跳过。三层叠加的结果是**定时任务可以随意补跑、重跑**。

再补一句设计哲学（面试官会记住这句）：

> 达人分成向上取整、尾差归集给公司，是因为**合作方对账时，少一分钱和被少一百块钱的信任伤害是一样的**。这不是算法问题，是商业问题。

**第 3 步：权限与审计（60s）**

不说"我做了 RBAC"，说**三级校验**：

```
第 1 级 功能权限  能不能调这个接口（39 个权限点，动作级拆分）
第 2 级 数据范围  能看哪些行（商务只看自己负责的达人 → 防止互相挖客户）
第 3 级 资源归属  这一条数据是不是你的
```

第 3 级的必要性用一句真实攻击路径说明：**"列表接口过滤了 ≠ 详情接口安全，真实越权路径是猜一个别人的 UUID 直接访问详情接口"**——所以每个按 ID 操作的入口都要重新校验。

审计则是**横切能力**：`@Audit({ action, resource })` 声明在 Controller 上，拦截器统一记录操作人、前后快照、IP、UA、请求 ID、耗时、成功与否，密码令牌证件号自动脱敏。为什么用拦截器而不是 Service 埋点：**人工埋点一定会漏（尤其后续新增接口），而审计是合规刚需**。

**第 4 步：AI 治理（90s）——如果面的是 AI PM，这里要加时**

四个抓手，逐个报数：

| 抓手 | 做法 | 一句话价值 |
| --- | --- | --- |
| 幂等 | `idempotencyKey` 唯一约束 | 防住"用户狂点按钮重复扣费"——AI 成本治理里最容易被忽略、也最烧钱的一项 |
| 熔断 | 月度预算用尽拒绝新任务（**HTTP 402 + 明确文案**，不是笼统 500） | 由管理者决定是否调高，而不是静默烧钱 |
| 校验 | LLM 输出过 zod 结构校验，失败分 `INVALID_OUTPUT` / `SCHEMA_MISMATCH` 并保留原文 | 模型会"看起来正确"地返回缺字段 JSON，写库后前端才炸，排查成本极高 |
| 度量 | 每任务落库 token / 成本(分) / 耗时 / 重试 / 降级原因 / **人工采纳率** | 直接回答"AI 花在哪、值不值" |

再加两条我认为最值得说的**边界感**：

> 第一，**Prompt 放在数据库而不是代码里**，因为它是运营资产、迭代频率远高于代码；配一条硬约束：**已被任务使用过的模板禁止就地修改，必须新建版本**——否则历史任务的 `templateId` 指向同一行却对应两套 Prompt，事后无法复盘。
>
> 第二，我给自己划了红线：**不得把模型输出当作事实写回数据库的关键字段**。AI 不能改结算金额、不能改达人状态、不能改合同条款；传给模型的数据也必须最小化（传达人身份证号给模型是重大合规事故）。**AI 只做建议与加速，钱和权的判断权始终在人手里。**

**第 5 步：工程化与可验证性（30s）**

- CI 四道关按"反馈速度"排序：静态校验（约 1 分钟，无需数据库）→ 单测（含覆盖率阈值，卡在结算与权限代码上）→ 集成（真 PostgreSQL + Redis，`migrate deploy` + **连跑两次 seed 验证幂等**）→ 构建；
- 自研 `check-prisma-usage.mjs`：在**没有 Prisma 客户端**的环境下静态校验 88 个源文件的模型名/枚举名一致性，且**自带自检**避免校验器出错时给假绿；
- AI 与采集都内置确定性 Mock Provider：**没有 API Key 也能跑通整条链路**，前端联调、CI、演示、客户 Demo 全部可用。

### 2.3 只用 3 个数字记住这个项目

| 数字 | 含义 |
| --- | --- |
| **39** | 权限点数量（动作级拆分，不是"角色对不对"） |
| **3** | 幂等层数 / 权限校验级数（同一个数字，两套机制） |
| **1** | 结算引擎里那条恒等式：`平台费 + 公司 + 达人 === 总流水` |

## 3. 追问应对（面试官最可能问的 8 个问题）

### Q1：为什么不做微服务？

> 因为**分布式事务与联调成本远大于收益**。这是内部工具，模块不会由不同团队独立发布，也不需要独立扩缩容。
>
> 我的取舍标准是写下来的：只有当"模块由不同团队独立发布、且需要独立扩缩容"时才引入微服务。同理我没引入消息队列（当前唯一异步场景是定时任务与采集，`@nestjs/schedule` 足够，需要削峰或事件驱动多消费者时才引入）、没引入 GraphQL（页面与接口基本一对一，REST 更易缓存排错）、没引入 UI 组件库、没用 ORM 二级缓存（缓存与库不一致是资金系统的灾难来源，只读报表成瓶颈时应该上物化视图）。

**这个回答的加分点**：不是"我不会微服务"，而是"我有明确的触发条件表"。

### Q2：金额为什么不能用浮点？你怎么保证不出错？

> 浮点无法精确表示 0.1，多级抽成后尾差会累积到元级。财务对账出现"三笔加起来比总流水少一分"时，**解释成本远高于改造收益**。
>
> 我的做法是三层：存储用 `Decimal(18,2)`；计算全部转「分」的整数；比率用基点整数。然后关键一步是**公司分成用"净额 － 达人分成"反推而不是独立相乘**——这样守恒是恒等式而非近似。最后每次计算都断言守恒，不满足就抛错。

### Q3：如果定时任务被重复执行/多个实例同时跑，会重复出账吗？

> 不会，有三层保护（这也是我设计时最先想的场景，因为**重复出账是最严重的资金事故**）：
> 1. 结算单 `(creatorId, periodStart, periodEnd)` 数据库唯一约束；
> 2. 明细 `idempotencyKey` 唯一（`STI:{creatorId}:{contractId}:{contentId}`），且用 `skipDuplicates`；
> 3. 已存在且非作废的单据直接跳过，不会覆盖已审批金额。
>
> 另外**逐人独立事务**：500 个达人里有 3 个数据异常，不该让 497 个也结不出来；失败的会进 `skippedReasons`，运营能看到"谁没结、为什么没结"，而不是一个笼统的 500。
>
> **但我要诚实说一个已知限制**：多实例部署时定时任务会在每个实例触发。业务幂等保证不会出错数据，但会产生重复日志与无谓数据库压力。部署文档里给了三个方案（独立 worker 进程最推荐 / Redis 选主锁 / 单实例），**代码目前还没内置这个开关**。

### Q4：合同冲突怎么办？比如两份合同同时生效。

> **直接报错，不猜**。两份合同同时生效时任何自动选择都是猜，猜错就是真金白银的错。所以结算遇到 ≥2 份生效合同时抛 422，并列出冲突合同编号，要求人工先关闭冲突合同。
>
> 而且这个校验是**双重**的：合同提交时校验区间冲突，审批时再校验一次——因为提交后可能有人插队。

### Q5：半年后达人质疑某笔金额少了，你能解释吗？

> 能，这是我设计时就留的。每条结算明细都有 `calculationTrace`（JSON），记录完整计算过程快照：总流水 → 平台费 → 净额 → 达人分成 → 代扣税，含阶梯命中的说明。**任何一笔都能复算复现。**
>
> 另外调整金额（补款/扣款）是**单独存** `adjustmentAmount` 的，`netPayable` 保持明细汇总值不变，实际支付 = `netPayable + adjustmentAmount`。这样明细与合同口径始终可复算，调整原因单独留痕。
>
> 历史任务的 `renderedPrompt`（渲染后的完整 Prompt）也一样落库，出问题能精确复现。

### Q6：你怎么判断一个 AI 功能该不该继续做？

> 这是我作为 AI PM 最在意的一条。我给自己定了一条硬标准写进了团队规范：
>
> **一个 AI 能力只有在「有人真的在用（采纳率可查）」且「单位成本可接受（成本可查）」时才值得保留。**
>
> 所以每个 AI 任务都必须落库 token、成本、耗时、以及**人工反馈（1 采纳 / -1 拒绝）**，`GET /api/ai/usage` 直接回答三个问题：花了多少、花在哪类任务、采纳率多少。
>
> **没有度量就没有迭代依据，也没有砍掉的依据**——这是很多 AI 功能上线后最缺的一环。

### Q7：AI 输出不可靠怎么办？比如返回的 JSON 缺字段。

> 输出不可靠是**必然**，不是意外，所以要在写入业务页面之前拦住：
>
> 1. 每个任务类型有 zod 结构校验（用 `passthrough` 允许模型多返回字段，不因此判失败）；
> 2. JSON 解析失败 → `INVALID_OUTPUT`，保留原文；结构不符 → `SCHEMA_MISMATCH`，列出具体不符字段；
> 3. 两种失败都保留原始输出，让人能判断"是 Prompt 约束不够还是模型能力不足"；
> 4. 主 Provider 失败会降级备用，但**降级必须状态可见**（`FALLBACK_USED` + 原因），前端会提示用户"本次结果由降级模型生成"，不能静默降级让用户误判质量。

### Q8：这个项目有什么不足？（必答题，要答得比面试官预期的更具体）

> 最要紧的是**可验证性**。项目开发环境是受限沙箱，`pnpm install`、`prisma generate`、`vitest` 都跑不起来（`spawn EPERM`），所以：
>
> - 我写了结算引擎的属性式穷举测试（300+ 组参数验证守恒不变量）和权限矩阵测试，但**它们还没有在正常环境执行过**；
> - 前端 0 个测试文件，`strict / noUnusedLocals` 这些 TS 约束实际上**从未被编译器验证过**；
> - 更关键的是我发现**迁移目录只有 2 个手写 SQL，没有 Prisma 生成的初始建表迁移**——这意味着 18 张业务表目前可能只能靠 `prisma migrate dev` 在开发库即时创建，而生产唯一允许的 `prisma migrate deploy` 无法在干净库建出表结构；
> - 还有两处会让 CI 第一道关直接失败的缺口：`apps/api` 声明了 lint 脚本但**没有 eslint 依赖与配置**；`docker-compose.yml` 指向的 **`apps/api/Dockerfile` 不存在**。
>
> 所以如果有人问我"完成了吗"，我的回答是：**代码与文档层面完成了，工程验证层面还没有**。我宁可主动把这个清单交出去，也不想在真正跑起来的时候才发现问题——这也是为什么我把这份清单直接写进了 README 的"未能验证"章节。

**为什么这样答最有说服力**：面试官问"不足"时，真正想确认的是**你有没有能力发现自己的问题**。上面这一串连 CI 会因为缺 eslint 配置而失败、迁移文件不足以建库这种细节都点出来了，比任何"我会加强学习"都有力。

## 4. 诚实边界卡（背下来，别被问倒）

| 已具备 | 尚未具备 |
| --- | --- |
| 结算引擎纯函数 + 守恒断言 + 三层幂等 | 单测/e2e **未在正常环境执行过** |
| 39 权限点三级校验 + 声明式审计 | 前端 **0 测试**，TS strict 未被编译器验证 |
| AI 成本熔断 + 采纳率 + 结构化校验 + 降级可见 | 采纳率**未与内容效果指标关联**（只统计人工反馈） |
| 确定性 Mock Provider（AI + 采集） | **真实平台采集是适配器骨架**，需企业资质与逐平台联调 |
| 定时任务 6 个（含月度结算生成） | **多实例定时任务未做选主**（业务幂等兜底） |
| 幂等种子数据 + 业务自洽演示数据 | **初始建表迁移缺失**，`migrate deploy` 干净库路径未验证 |
| CI 四道关设计完整 | **api 侧无 eslint 配置**、**`apps/api/Dockerfile` 缺失** → 第一关与全栈容器化当前会失败 |
| 密钥以 `v1` 前缀预留轮换 | **密钥轮换双读迁移未落地** |

## 6. 一页速查卡（面试前 2 分钟看这个）

```
定位：达人合作的资金结算中台（不是达人管理系统）
链路：找达人 → 谈合同 → 做内容 → 看数据 → 算钱 → 打款
```
