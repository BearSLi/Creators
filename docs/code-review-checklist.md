# 代码审查清单

> JD 要求「具备较好的代码审查能力，能识别代码质量、边界条件、安全隐患和可维护性问题」。
> 本文是本项目的审查标准，也是 PR 自查清单。**审查的目标不是找错，而是让下次不会犯同样的错**——所以每条都写清了「为什么」。

---

## 使用方式

1. 提 PR 前作者按此清单自查（尤其「资金与状态」「安全」两节）。
2. 审查者按此清单逐项确认，发现的问题**给出具体理由与替代方案**，不写「建议优化」。
3. 新增的通用规则沉淀回本文档——这是规范能活下来的唯一方式。

---

## 一、资金与金额（最高优先级）

- [ ] **金额是否全程用整数「分」或 `Decimal`？** 出现 `parseFloat` / `toFixed` 参与运算 / `Number` 除法都要打回。浮点误差在多级分成后会累积到元级。
- [ ] **比率是否用基点整数（bp）？** 存储 `0.7` 这类浮点会在序列化与比较中产生歧义。
- [ ] **舍入方向是否显式指定且可解释？** `applyBp(amount, bp, 'down' | 'up' | 'nearest')` 必须明确传参。默认「四舍五入」在资金链路里是不够的：平台费与公司分成向下取整、达人分成向上取整，尾差归公司——这是业务规则，不是实现细节。
- [ ] **金额是否守恒？** 任何多级分配都要断言 `各部分之和 === 总额`。项目里用抛出异常而非跳过，因为不守恒意味着代码有缺陷，静默容忍会产出错误账目。
- [ ] **是否在前端计算金额？** 前端只能展示与格式化，不得做加减后回写。
- [ ] **数据库写入是否为 `Decimal` 字符串？** 传 `number` 给 Prisma 的 Decimal 字段会引入精度风险。
- [ ] **调整项是否与计算值分离？** 结算的 `netPayable` 保持「明细汇总值」，补款/扣款走 `adjustmentAmount` + 原因。混在一起会让明细与合同口径无法复算。
- [ ] **金额变更是否有权限与状态保护？** 已审批金额必须冻结（`assertSettlementTransition` + 状态判断）。

## 二、边界条件

- [ ] **零值与极小值**：`0` 流水、`1` 分流水、`0` 转化数、空数组、空字符串是否都验证过？
- [ ] **除零**：任何除法前确认分母非零（如「平均每条内容收入」在内容数为 0 时）。
- [ ] **负数**：金额、数量、页码。负数流水必须走调整项而不是直接计算。
- [ ] **溢出与精度**：`BigInt`（播放量）转 `Number` 前确认范围；`Decimal(18,2)` 上限是否够用。
- [ ] **空集合聚合**：`aggregate._sum` 在无匹配行时返回 `null`，是否用 `?? 0` 处理？
- [ ] **分页边界**：`page` 超出总页数、`pageSize` 超上限（本项目最大 100）、`skip` 计算。
- [ ] **日期边界**：账期用闭区间还是半开区间？跨月/跨年/闰年 2 月/月末 23:59:59.999 是否正确？（有对应单元测试）
- [ ] **时区**：日期比较是否统一 UTC？账期用 `@db.Date` 而非 timestamp 以避免时区偏移。
- [ ] **字符串边界**：超长输入是否截断（`maxLength`）？空字符串与 `null` 语义是否区分？
- [ ] **数组边界**：空数组 vs `undefined` 在 Prisma 中的语义完全不同（`in: []` 匹配零条，`undefined` 忽略条件）。这是极易出错的地方。
- [ ] **集合大小**：批量操作是否有上限？（本项目批量导入上限 200 条）
- [ ] **并发边界**：同一资源被同时修改会怎样？唯一约束、事务重试、乐观锁是否到位？

## 三、安全

- [ ] **越权访问**：新增的详情/编辑/删除接口是否做了**资源归属校验**（`assertOwnership`）？只靠列表接口过滤是不够的——攻击路径是「猜 UUID 直接访问详情」。
- [ ] **数据范围**：列表接口是否应用了 `buildScopeFilter(user)`？
- [ ] **权限声明**：Controller 是否有 `@RequirePermissions`？（全局 `JwtAuthGuard` 只保证登录，不保证权限）
- [ ] **敏感操作实时复核**：审批/打款/改权限是否额外调用 `assertFreshPermission`？（access token 内嵌权限最长滞后 2 小时）
- [ ] **DTO 白名单**：新字段是否在 DTO 中声明？`forbidNonWhitelisted` 会拒绝未声明字段，防止客户端注入 `status` / `ownerId` / `createdById` 这类本不该由前端控制的字段。
- [ ] **排序字段白名单**：`sortBy` 是否通过 `resolveOrderBy` 限定在允许字段内？直接拼接字段名到 `orderBy` 是 SQL 注入面。
- [ ] **SQL 原始查询**：`$queryRaw` 是否使用参数化（模板字符串标签形式 `` $queryRaw`... ${value}` ``）而非字符串拼接？
- [ ] **敏感数据存储**：证件号/银行卡号是否加密（`encryptSensitive`）？
- [ ] **敏感数据返回**：手机号/真名/微信号是否按权限脱敏？列表与详情是否共用同一个映射函数（避免两处逻辑不一致）？
- [ ] **日志泄露**：日志与审计中是否出现密码、令牌、证件号？审计拦截器已自动脱敏 `SENSITIVE_BODY_KEYS`，新增敏感字段名要加进去。
- [ ] **错误信息泄露**：错误响应是否包含堆栈、SQL、文件路径？全局过滤器已处理，但自定义异常不要塞敏感 `details`。
- [ ] **认证**：涉及登录/令牌的改动是否保持「等成本比对」（防时序枚举）、失败计数、锁定策略？
- [ ] **幂等键来源**：`idempotencyKey` 是服务端生成还是客户端传入？若由客户端传入，是否会与他人冲突（本项目用 UUID，且唯一约束兜底）？
- [ ] **文件与导出**：导出接口是否要求独立权限（`*:export`）？导出内容是否含超出权限的字段？

## 四、状态与业务规则

- [ ] **状态流转是否走状态机**？是否有人绕过 `assertTransition` 直接 `update({ status })`？绕过会破坏「合同才能结算」这类前置约束。
- [ ] **非法流转的返回是否有用**？本项目返回 `allowedNext`，让前端能渲染合法操作——比一个裸 409 有价值得多。
- [ ] **高风险流转是否强制填原因**？（解约、拉黑、合同终止、结算调整、作废）
- [ ] **前置条件是否校验**？例如：排期内容前达人已签约、生成结算前合同生效、发布内容前审核通过。
- [ ] **删除保护**：删除前是否检查关联数据？本项目采用「有关联则拒绝 + 提示替代操作（改用解约）」，而不是级联删除。
- [ ] **不可变原则**：生效中的合同能否改分润？已审批的结算能否改金额？已发布的内容能否改标题？——这三处必须拒绝，因为它们是**历史凭证**。
- [ ] **双人复核**：资金与合同的创建人是否被阻止审批自己的单据？
- [ ] **业务规则与代码一致**：代码里的规则是否与文档/合同模板一致？不一致时以业务确认为准并同步文档。

---

## 五、数据与事务

- [ ] **事务边界**：多表写入是否在同一事务内？编号分配是否传入了 `tx`？（传 `tx` 才能与业务写入同生共死，避免编号空洞或业务成功但编号未分配）
- [ ] **事务内的失败处理**：事务内不要做外部调用（HTTP/AI）。长事务会持有锁，且外部调用失败无法回滚已发出的请求。
- [ ] **幂等**：重复执行会不会产生重复数据？三层机制是否到位（唯一约束 / 幂等键 / 状态跳过）？
- [ ] **N+1 查询**：循环里是否有数据库查询？用 `include` / `findMany({ where: { id: { in: ids } } })` 批量取。
- [ ] **索引**：新增查询条件是否有对应索引？高频列表是否走全表扫描？（写查询时同步想索引）
- [ ] **软删除**：查询是否都带了 `deletedAt: null`？忘记加会把已删除数据查出来。
- [ ] **唯一约束**：业务唯一性是否交给了数据库，而不是只在应用层判重（有竞态）？
- [ ] **连接池**：新增的并发查询是否考虑池大小？（本项目 `DATABASE_POOL_SIZE` 可调）

## 六、错误处理与可观测性

- [ ] **异常类型**：是否使用了项目定义的业务异常（`BusinessException` / `StateConflictException` / `ResourceNotFoundException` …）并带稳定 `code`？抛裸 `Error` 会变成 500 且前端无法差异化处理。
- [ ] **错误信息是否可操作**？「操作失败」是无用的；「该达人存在 2 张未结清结算单，请先完成结算或勾选强制终止」才是有用的。
- [ ] **错误提示是否在说真话？** 文案声称的与代码实际做的是否一致。本项目踩过一次：提示写「请检查**标红字段**后重试」，而前端**从不消费**后端的字段错误去标红 —— 用户被指引去看一堆并不存在的红字段。**任何「请用户去看某个 UI 状态」的提示，都必须验证那个状态真的会被设置出来。**
- [ ] **「用于标红的字段」与「用于展示的原因」是否分开了？** 有一类校验错误没有对应输入框（`forbidNonWhitelisted` 拦下的「多传未声明字段」）。若提示只从字段映射里取内容，这类错误会让提示退化成泛化兜底。展示必须用完整消息列表。
- [ ] **前端是否在解析错误文本做逻辑判断？** 判断依据只能是 `code` 与结构化的键（如 `fieldErrors`），绝不能正则去捞 `message` 里的英文句子 —— 文本会被翻译、会被改写。
- [ ] **校验错误是否带结构化字段名？** 只返回「xxx must be a UUID」这种句子，调用方无法可靠标红。后端应给出 `{ 字段名: [消息] }`（本项目为 `fieldErrors`，见 [api.md §2.3](api.md)）。
- [ ] **审计埋点**：写操作是否有 `@Audit(...)`？`action` / `resource` / `summary` 是否准确（审计日志的可读性直接决定排查效率）？
- [ ] **日志级别**：正常业务流转用 `log`、可恢复问题用 `warn`、需要人工介入用 `error`。是否避免了在循环里刷 `error`？
- [ ] **日志内容**：是否包含可用于定位的标识（业务编号、用户、账期），而不是只有「失败」？
- [ ] **降级是否可见**：降级成功不能静默——本项目记为 `FALLBACK_USED` 并在接口返回 `fallbackReason`，前端提示用户。

## 七、代码质量与可维护性

- [ ] **命名**：变量/函数名是否表达业务含义？（`calcSettlement` 优于 `process`）
- [ ] **函数长度与职责**：单个方法是否超过约 60 行？是否只做一件事？
- [ ] **重复逻辑**：相同规则是否出现在多处？（金额逻辑必须单点；脱敏映射必须单点）
- [ ] **魔法数字**：是否把 `10000`（基点分母）、`30`（账期天数）等抽成常量或配置？
- [ ] **注释解释「为什么」**：项目规范要求注释说明设计意图与权衡，不写「这是查询语句」。看到 `// 幂等第 2 层`、`// 尾差归集给公司` 这类注释才算合格。
- [ ] **分层越界**：Controller 是否写了业务判断？Service 是否被绕过直连 Prisma？
- [ ] **纯函数优先**：可抽成纯计算的逻辑是否抽了？（结算引擎、状态机、渲染器都是纯函数，才可能有穷举测试）
- [ ] **类型安全**：是否出现 `any` / `as unknown as` / `@ts-ignore`？如果是，必须有注释说明为什么无法避免。
- [ ] **未使用代码**：是否遗留了 `console.log`、注释掉的代码块、未使用的 import？（`noUnusedLocals` 会在 CI 拦住一部分）
- [ ] **配置而非硬编码**：阈值、开关、超时是否走环境变量或数据库配置？

## 八、跨边界一致性（前端 / 后端 / 数据库）

> 这一节是项目里**代价最高**的一类 bug 换来的。它们的共同特征：**TypeScript 与单元测试都发现不了**。
> 前端枚举声明和使用它的页面都在前端这一侧，`data.status === 'PENDING'` 两边都取自同一个手写联合类型，
> 类型系统只能保证「前端和自己一致」，不能保证「前端和后端一致」。只有引入另一侧的事实（`schema.prisma`、OpenAPI）才能发现。

- [ ] **枚举是否与后端 `schema.prisma` 逐个成员一致？** 多了、少了、拼错都算错。跑 `pnpm enum:check`。注意「多了」比「少了」更隐蔽：前端多一个不存在的状态，比较分支永远不命中，筛选直接 400，但**不会报任何错**。
- [ ] **页面里是否直接裸写了状态字面量？** 应统一走 `constants.ts` 的常量表。裸写 `'CANCELLED'`（后端是 `CANCELED`）这类拼写差异是本项目真实发生过的事故。
- [ ] **可比较的字段是否声明成了 `string`？** `PendingTodo.type: string` 让 `map.set(todo.type, ...)` 与三个编造的键「类型上都成立」，结果是侧边栏红点一个都不显示。**该声明成枚举的地方声明成 `string`，等于关掉了这一整类检查。**
- [ ] **枚举的中文标签表是否覆盖全部成员？** 漏一个就会在页面上渲染出 `undefined`。
- [ ] **后端是枚举、前端是自由文本的字段，取值是否与后端约定一致？** 例如 `Tag.category`（后端 DTO 注明 `capability`/`category`/`risk`/`custom`，前端曾提交 `STYLE`/`SCENE`/…）。这类字段不会报错，只会**静默写入没人认识的分类**。
- [ ] **提交前是否对照过后端 DTO？** `forbidNonWhitelisted` 会拒绝未声明字段，跑 `pnpm contract:verify`。
- [ ] **「类型检查通过」是否真的检查了东西？** 新增/修改前端工程配置后，故意改坏一处类型确认它报错——本项目 `tsc --noEmit` 曾因指向 solution 配置而检查 0 个文件，却一直报 0 error。

## 九、测试

- [ ] **核心逻辑有测试**：新增或修改了结算、权限、状态机、金额工具的代码，是否同步更新测试？
- [ ] **测行为而不是实现**：断言「计算结果与不变量」而不是「调用了某个内部方法」。
- [ ] **覆盖边界**：每个 `if` 的两个分支、每个错误抛出路径。
- [ ] **不变量测试**：资金类逻辑是否有属性式断言（穷举多组参数验证守恒）？
- [ ] **测试可读**：测试名说明业务含义（`'尾差归集给公司，达人分成向上取整'` 优于 `'test calc case 3'`）。
- [ ] **不依赖外部服务**：单元测试不得调用真实 AI / 平台接口（用 mock provider）。
- [ ] **校验脚本自身是否被验证过？** 新增一致性校验脚本时，必须有 `--self-test`（用构造数据证明它**确实会报错**）。一个因为正则写坏而永远输出「通过」的检查脚本，比没有检查更危险。

## 十、前端专项

- [ ] **三态处理**：loading（骨架）/ 空状态 / 错误重试是否都有？
- [ ] **防重复提交**：提交类按钮是否 loading 且禁用？AI 任务是否带 `idempotencyKey`？
- [ ] **权限驱动 UI**：按钮与菜单是否根据权限隐藏/禁用？（后端仍会拦截，但前端隐藏能减少无意义的报错）
- [ ] **状态机驱动 UI**：状态操作按钮是否来自后端返回的 `allowedNext`，而不是前端硬编码状态图？
- [ ] **动作入口的前置条件是否与后端一致？** 「审核」按钮曾在 `status === 'PENDING_REVIEW'`（一个不存在的状态）下渲染，导致这个核心入口**永远不出现**。入口条件也要以后端可执行的状态为准。
- [ ] **错误码处理**：是否把 `code` 映射成中文提示？`details.allowedNext` 是否被利用？
- [ ] **金额展示**：是否使用 `MoneyText`（等宽、右对齐、千分位）？是否避免了前端计算？
- [ ] **401 处理**：并发 401 是否只刷新一次令牌？（未去重会引发刷新风暴，甚至触发重放检测把用户踢下线）
- [ ] **性能**：长列表是否虚拟化或分页？是否避免了每次渲染重建大对象？
- [ ] **可访问性**：表单 label、按钮 `type`、键盘可操作（内部工具也应有基本要求）

## 十一、文档与交付

- [ ] **接口变更**：`docs/api.md` 与 DTO 的 `@ApiProperty` 描述是否同步？
- [ ] **数据模型变更**：`docs/data-model.md` 与迁移是否同步？破坏性变更是否按三步法？
- [ ] **权限变更**：`docs/permissions.md` 矩阵表是否更新？是否同步了 `permissions.spec.ts` 的 `ADMIN_ONLY_PERMISSIONS`？
- [ ] **环境变量变更**：`.env.example` 是否补充并注释？是否在 `env.ts` 中校验？
- [ ] **AI 模板变更**：新增任务类型是否更新 `docs/ai-guidelines.md` 第 4 节？
- [ ] **部署影响**：是否需要停机？是否有多实例下的问题（定时任务、内存限流）？
- [ ] **PR 描述**：是否说明了「为什么这样改」与「如何验证」？截图或接口示例？

## 附：本项目最容易被审查出来的 7 类问题

按历史经验排序（也是审查时的优先关注点）：

| # | 问题 | 检查动作 |
| --- | --- | --- |
| 1 | 列表接口漏加数据范围过滤 → 商务看到别人的客户 | 搜该 Service 是否使用 `buildScopeFilter` |
| 2 | 详情接口漏做归属校验 → 猜 UUID 越权访问 | 搜该 Service 是否有 `assertOwnership` |
| 3 | 金额用了浮点 → 对账差几分钱 | 搜 `parseFloat` / `/ 100` / `toFixed` 参与运算 |
