# CreatorOps 架构设计

> 本文说明系统的分层与模块边界、关键链路的时序、技术选型的取舍，以及现阶段的已知限制。
> 目标是让新同事在半小时内理解「代码为什么长这样」，而不是只知道「代码在哪」。

### 分层规则（Code Review 时按此判断越界）

| 规则 | 原因 |
| --- | --- |
| Controller 只做参数绑定与权限声明，禁止写业务判断 | 业务规则集中到 Service，才能在多个入口（手动接口 + 定时任务）复用同一份逻辑 |
| Service 是唯一可以访问 Prisma 的地方 | 数据访问集中，便于加事务、审计、索引优化 |
| 跨模块调用走 Service，不直接读对方的表 | 模块边界即业务边界；直接读表会让「达人软删除」这类规则被绕过 |
| 金额/比率计算只能调用 `common/utils/money.ts` 与结算引擎 | 金额逻辑必须单点，否则迟早出现两套口径 |
| 纯计算逻辑抽成无 IO 的纯函数 | 结算引擎能被单元测试穷举，这是资金正确性的唯一可靠保障 |

## 2. 模块边界与依赖方向

```
                     ┌──────────────┐
                     │   common     │  (CodeGenerator 等)
                     └──────┬───────┘
                            │
   ┌────────────┬───────────┼───────────┬─────────────┐
   ▼            ▼           ▼           ▼             ▼
┌────────┐ ┌─────────┐ ┌─────────┐ ┌─────────┐  ┌──────────┐
│ auth   │ │ creators│ │ brands  │ │  users  │  │   ai     │
└───┬────┘ └────┬────┘ └────┬────┘ └─────────┘  └────┬─────┘
    │           │           │                        │
    │           ▼           ▼                        │
    │      ┌──────────────────────┐                  │
    │      │     contracts        │                  │
    │      └──────────┬───────────┘                  │
    │                 ▼                              │
    │      ┌──────────────────────┐                  │
    │      │  projects / contents │◄─────────────────┘ (合规预检/脚本生成)
    │      └──────────┬───────────┘
    │                 ▼
    │      ┌──────────────────────┐
    └─────►│    settlements       │  ← 定时任务也从此进入（同一段代码）
           └──────────┬───────────┘
                      ▼
              ┌───────────────┐
              │  dashboard    │  (只读聚合，不反向依赖)
              └───────────────┘

  横切：audit（@Global，任何模块可写审计）· health
```

**关键依赖约束**：

1. `settlements` 依赖 `contracts` 与 `contents` 的数据模型，但**不依赖它们的 Service**——结算只读已固化的金额字段，避免「结算时再触发采集」这类隐性耦合。
2. `scheduler` 依赖 `settlements` 而不是自己实现一套结算逻辑。**手动与自动必须走同一段代码**，否则两套实现的口径分歧是必然的。
3. `dashboard` 只读，不被任何模块依赖，可以随时替换成缓存实现而不影响业务。
4. `ai` 不依赖任何业务模块（只接收业务传入的数据），业务模块按需依赖 `ai`，保持 AI 能力可插拔。

## 3. 关键链路时序

### 3.1 结算生成（资金链路，最需要正确性）

```
定时任务(每月3日02:00) / 运营手动点击
        │
        ▼
SettlementService.generate(period)
        │
        ├─ ① resolvePeriod: 把「YYYY-MM」解析为 [月初, 月末] —— 账期口径固定为自然月
        │
        ├─ ② 拉取候选达人（状态 ∈ SIGNED/ACTIVE/PAUSED/TERMINATED）
        │
        └─ for each creator（逐个独立事务，单人失败不影响全局）
              │
              ├─ assertCanBeSettled(状态)             ← 不满足则记入 skippedReasons
              ├─ 查该账期是否已有结算单                ← 已存在非作废 → 跳过（幂等第 1 层）
              ├─ 查账期内生效的合同
              │     ├─ 0 份 → 跳过
              │     └─ ≥2 份 → 抛错并说明冲突合同      ← 口径歧义必须人工解决，不能猜
              │
              ├─ 拉取归因载体：账期内发布、有收入、且尚未产生结算明细的内容
              │     └─ settlementItems: { none: {} }   ← 幂等第 2 层：内容不重复结算
              │
              ├─ 对每一笔调用 calculateSettlement()（纯函数）
              │     ├─ 解析生效分成率（阶梯命中则覆盖）
              │     ├─ 逐级计算：平台费(下取整) → 净额 → 达人分成(上取整) → 公司分成(兜尾差) → 代扣税
              │     └─ 断言守恒：平台费 + 公司 + 达人 === 流水
              │
              └─ 单事务写入
                    ├─ 分配结算单号（code_sequences 原子自增）
                    ├─ 建结算单（头部金额 = 明细汇总）
                    ├─ 建明细（idempotencyKey 唯一，createMany skipDuplicates）
                    └─ 写 calculationTrace（每条明细的计算过程快照，可复算）
```

**为什么这么设计**

- **逐人独立事务**：500 个达人里若有 3 个数据异常，不应让 497 个也结不出来。
- **失败收集成 `skippedReasons`**：运营能看到「谁没结、为什么没结」，而不是一个笼统的 500。
- **合同冲突直接报错**：两份合同同时生效时任何自动选择都是猜，猜错就是真金白银的错。
- **`calculationTrace` 落库**：半年后达人质疑某笔金额时，能拿出当时的完整计算链路。

### 3.2 结算单据状态流转

```
      ┌──────────────────────────────────────────────┐
      │                                              │
   DRAFT ──提交──► PENDING_APPROVAL ──审批──► APPROVED ──打款──► PAID
      ▲                 │                      │                │
      │                 │ 驳回                 │ 争议           │ 争议
      │                 ▼                      ▼                ▼
      └──────────── DISPUTED ◄─────────────────┴────────────────┘
      │                 │
      └── VOID ◄────────┘
```

- **金额冻结规则**：只有 `DRAFT` / `DISPUTED` 允许调整金额。已审批的金额是财务对账依据，不允许变更——要改就先作废重开。
- **双人复核**：创建人不能审批自己生成的单据（系统内存在其他财务时强制生效）。
- **明细完整性闸门**：提交与审批前校验「明细汇总 === 单据头部金额」，拦住手改库、并发调整、历史迁移造成的静默不一致。

### 3.3 AI 任务执行

```
POST /api/ai/tasks
      │
      ├─ ① idempotencyKey 命中 → 直接返回既有结果（不重复扣费）
      ├─ ② 取该任务类型的可用 Prompt 模板（版本倒序 + 灰度筛选）
      ├─ ③ 变量校验（缺失必填变量直接报错，不消耗 token）
      ├─ ④ 渲染 Prompt（自研极简渲染器：不做表达式求值，单变量长度上限）
      ├─ ⑤ 预算预检（估算成本 + 本月已用 > 预算 → 402 明确告知）
      ├─ ⑥ 落库 RUNNING（保留渲染后的完整 Prompt，便于复现）
      │
      ├─ ⑦ 调主 Provider
      │     ├─ 可重试错误（超时/限流/5xx）→ 指数退避 + 抖动重试（默认 2 次）
      │     └─ 不可重试（鉴权/参数）→ 立即失败
      │
      ├─ ⑧ 主 Provider 最终失败 → 降级到备用 Provider
      │     └─ 成功则状态记为 FALLBACK_USED 并写明降级原因（前端会提示用户）
      │
      ├─ ⑨ 解析输出：抽取 JSON（容忍 ```json 包裹）→ zod 结构校验
      │     ├─ 解析失败 → FAILED + 保留原文（INVALID_OUTPUT）
      │     └─ 结构不符 → FAILED + 列出不符字段（SCHEMA_MISMATCH）
      │
      └─ ⑩ 回写结果、token、成本（分）、耗时、重试次数、finish_reason
            └─ finish_reason=length 说明被截断，会告警建议调高 maxTokens
```

**AI 成本治理的三个抓手**

1. **幂等**：`idempotencyKey` 唯一约束，前端重复点击不会重复扣费。
2. **熔断**：月度预算用尽拒绝新任务（HTTP 402 + 明确文案），由管理者决定是否调高。
3. **可观测**：每任务的 token/成本/耗时/采纳率都落库，`GET /api/ai/usage` 直接回答「AI 花在哪、值不值」。

### 3.4 认证与令牌刷新

```
登录 ──► access token (2h, 内嵌权限集合) + refresh token (14d, 只存 sha256 哈希)
              │
   业务请求 ──► JwtAuthGuard（不查库，靠短有效期 + 权限内嵌保证性能）
              │
   401 ──► 前端用 refresh token 换新令牌（并发去重，只刷新一次）
              │
              ├─ 校验库中记录：存在/未撤销/未过期/family 一致
              ├─ 轮换：撤销旧 token，签发新 token，记录 replacedByTokenId
              └─ 若旧 token 被二次使用 → 判定泄露 → 撤销整个 family 并强制重登
```

**为什么不每次请求查库校验权限**：鉴权查询会成为最高频查询，QPS 高时拖垮数据库。代价是最长 2 小时的权限滞后，用两个手段弥补：① refresh 时查库校验账号状态；② 敏感操作（审批/打款/改权限）在 Service 层额外做一次实时权限复核（`assertFreshPermission`）。

## 4. 关键设计决策与取舍

### 4.1 金额为什么用「分」的整数与基点整数

浮点数无法精确表示 0.1，多级抽成后尾差会累积到元级。财务对账出现「三笔加起来比总流水少一分」时，解释成本远高于改造收益。因此：

- 存储：`Decimal(18,2)`（数据库层面精确）
- 计算：全部转为「分」的整数
- 比率：基点整数（`1000` = 10%），避免 `0.1` 这类浮点表示

### 4.2 尾差为什么归集给公司（达人分成向上取整）

多级链路每条都四舍五入时，累计误差可能让达人少拿几分钱。**合作方对账时，少一分钱和被少一百块钱的信任伤害是一样的**。所以达人分成向上取整、公司分成兜住剩余尾差，并保证 `平台费 + 公司 + 达人 === 流水` 恒等。

### 4.3 为什么把 Prompt 放在数据库而不是代码里

Prompt 是运营资产，迭代频率远高于代码。放库里可以：版本化（效果变差可回滚）、灰度（`rolloutPercent`）、无发布迭代（运营自己改）。配套约束：**已被任务使用过的模板禁止就地修改 Prompt 内容**，必须新建版本——否则历史任务的 `templateId` 指向同一行却对应两套 Prompt，事后无法复盘。

### 4.4 为什么审计用拦截器而不是 Service 埋点

人工埋点一定会漏（尤其后续新增接口），而审计是合规刚需。`@Audit({ action, resource })` 声明在 Controller 上，拦截器统一记录。审计写失败只记应用日志、不回滚业务——代价是可能丢极少量记录，换来的是「审计表抖动不会导致业务不可用」。若合规要求 100% 不丢，应改为写本地文件/Kafka 后异步入库。

### 4.5 为什么用软删除 + 业务链路保护

业务数据永不物理删除（`deletedAt`）。删除达人前检查是否关联合同/内容/结算——有关联时拒绝删除并提示改用「解约」。这让历史报表、结算凭证、审计追溯始终有依据。

### 4.6 刻意不引入的技术与理由

| 没引入 | 理由 | 什么情况下才该引入 |
| --- | --- | --- |
| 微服务 | 内部工具团队规模小，分布式事务与联调成本远大于收益 | 模块由不同团队独立发布、且需要独立扩缩容时 |
| 消息队列 | 当前唯一异步场景是定时任务与采集，`@nestjs/schedule` 足够 | 需要削峰（如批量导入十万级）、事件驱动多消费者时 |
| GraphQL | 前端页面与接口基本一对一，REST 更易缓存、易排错 | 多端（Web/App/小程序）需要差异化字段裁剪时 |
| UI 组件库 | 设计令牌 + 手写组件更贴合业务表格/表单密度需求，且无升级负担 | 需要大量复杂交互组件（富文本、虚拟表格）时 |
| ORM 二级缓存 | 缓存与库不一致是资金系统的灾难来源 | 只读报表类接口成为瓶颈时，用物化视图而非二级缓存 |

## 5. 并发、一致性与幂等

| 场景 | 风险 | 处理方式 |
| --- | --- | --- |
| 同一账期重复生成结算 | 重复出账（最严重的资金事故） | 唯一约束 `(creatorId, periodStart, periodEnd)` + 明细 `idempotencyKey` + 已审批跳过 |
| 多实例定时任务同时触发 | 同一任务跑多次 | 业务层幂等；生产建议选主或独立 worker |
| 业务编号并发分配 | 编号重复撞唯一索引 | `INSERT ... ON CONFLICT DO UPDATE ... RETURNING` 原子自增，且在业务事务内 |
| 合同区间并发提交 | 出现两份同时生效的合同 | 提交与审批时都做区间冲突校验（审批时复查，因为提交后可能有人插队） |
| 结算金额并发调整 | 头部金额与明细不一致 | 审批前 `assertItemIntegrity` 校验；金额只在草稿/争议态可改 |
| 乐观并发冲突 | 事务失败 | `withTransaction` 对 P2034/P2028 做指数退避重试（最多 2 次 + 抖动） |
| AI 重复点击 | 重复扣费 | `idempotencyKey` 唯一约束 |
| Refresh token 重放 | 令牌泄露被长期利用 | 轮换 + family 重放检测 → 撤销整族强制重登 |

## 6. 性能与可观测性

**已做的性能设计**

- 索引按真实查询路径设计：达人库复合索引 `(status, tier)`、`(deletedAt, createdAt)`；快照表 `(accountId, statDate)` 唯一；审计 `(resource, resourceId, createdAt)`。
- 列表接口一律「`$transaction([findMany, count])`」并行取数与总数，避免两次串行往返。
- 看板趋势用 `date_trunc` 在数据库侧聚合，不把明细拉到应用层分组。
- 分页上限 100（`MAX_PAGE_SIZE`），导出走分批拉取，避免一次性把全量数据读进内存。
- 开发环境打印 >300ms 的慢查询，便于上线前发现 N+1。

**可观测性**

- 请求 ID（`X-Request-Id`，可由网关传入）贯穿响应、错误与审计记录。
- 结构化日志（pino），生产 JSON 格式便于采集。
- 健康检查分存活（不查依赖）/就绪（查数据库）两个探针——数据库抖动时避免容器被反复重启放大故障。

**后续优化路线**（按触发条件，不是按「技术先进性」）

1. 内容表到千万级 → 引入按天预聚合表 + Redis 缓存看板（改动限制在 `DashboardService` 内，接口契约不变）。
2. 采集任务量上升 → 引入 BullMQ 队列与独立 worker，采集与 Web 进程分离。
3. 审计写入成为热点 → 异步批量写 + 分区表（按 month 分区）。

## 7. 安全设计清单

| 面向 | 措施 |
| --- | --- |
| 认证 | bcrypt(12) 哈希；登录失败 5 次锁定 15 分钟；用户不存在时也做等成本比对（防时序枚举） |
| 令牌 | access/refresh 双密钥且启动时校验不相等；refresh 只存哈希；轮换 + 重放检测 |
| 授权 | 功能权限 + 数据范围 + 资源归属三级；敏感操作实时权限复核 |
| 输入 | `whitelist + forbidNonWhitelisted`（防止客户端注入 `status`/`ownerId` 等本不该控制的字段）；排序字段白名单（SQL 注入面） |
| 敏感数据 | 证件号 AES-256-GCM 加密存储；手机号/微信/姓名按权限脱敏；导出需独立权限 |
| 审计 | 写操作全覆盖；入参中的密码/令牌自动脱敏；审计查询本身需 `audit:read` |
| 传输与响应头 | Helmet；生产 CORS 白名单；错误响应不含堆栈与 SQL |
| 启动安全 | 生产环境弱密钥/相同密钥直接拒绝启动（fail fast） |
| 文档暴露 | Swagger 仅非生产环境开放 |

## 8. 已知限制

1. **平台采集为骨架**：`HttpCollectorDriver` 具备鉴权/超时/重试/错误转换的完整结构，但真实平台接入需企业资质与逐平台联调；`MockCollectorDriver` 提供确定性仿真数据。
2. **白标多租户未实现**：当前为单公司内部系统，`Team` 提供组织维度，但未做数据租户隔离。
3. **实时通知仅站内**：`Notification` 表 + 站内提醒；未接企微/钉钉机器人（预留 `ALERT_WEBHOOK_URL`）。
4. **密钥轮换未落地**：密文带 `v1` 前缀预留了轮换空间，双读迁移尚未实现。
5. **定时任务单实例假设**：见「并发与一致性」表。
6. **export 走 CSV**：财务实际用 Excel，CSV 兼容性最好；未做 xlsx 服务端生成（避免引入重依赖）。
